# Execution Plan

The Execution Plan pane shows the captured [execution plan](https://learn.microsoft.com/en-us/sql/relational-databases/performance/execution-plans) as a tree of operators, connected to the [Timeline](/docs/user-guide/query/Timeline):

![Execution Plan with an operator selected during replay](/docs/user-guide/images/query-hash-match-build-running-cropped.png)

Each operator shows its name, object, and cost percentage, plus a small bar tracking its progress as the replay runs. Operators that consume more than one input, like a Hash Match join, label each input - **Build** and **Probe** for a hash join. See the [Showplan operators reference](https://learn.microsoft.com/en-us/sql/relational-databases/showplan-logical-and-physical-operators-reference) for what each operator does.

During replay the plan animates what is happening at the playhead - active operators highlight, rows streaming between operators are drawn as moving flow lines (thicker lines carry more rows), and operators blocked waiting on their input are marked. The plan can be zoomed with **Ctrl + mouse wheel** and panned by dragging.

For a [Full Trace](/docs/user-guide/query/FullTrace) run the plan draws each connection as the iterator calls that run along it, and follows the [Trace Timeline](/docs/user-guide/query/TraceTimeline) playhead. A dotted line points from each operator to the input it asks for rows, and a solid line points back with the response. Each input has its own pair of lines, hidden until a call lights them. Every line is the same width, and the costs and the streaming and blocked flow lines are left off. The dotted line shows in green while a GetRow or GetNextBatch call to the input is running. When the call returns a row or a batch, the solid line shows in green. When the playhead moves on, a line fades away over a time that follows how often it lights. A line that lit a while ago fades slowly, and one that lights again straight away switches off at once, so a fade never runs into the next one and the requests and responses can be seen ticking across the plan at any speed. The lit parts of the operator icons fade the same way.

The operator icons light up from the [Trace Timeline](/docs/user-guide/query/TraceTimeline#operator-tracks)'s operator tracks as well. A rule with a **Plan Part** lights that part of the icon in the rule's colour while one of its calls is running, or when one of its calls returned in the playhead's last move. The predefined **Seek** track lights a seek's root, intermediate and leaf nodes as it reads each page on its way down the b-tree.

With the **Open** track turned on, each operator's icon is grey until the track's tick shows it in colour, from the operator's Open call until it is closed. The track starts off, and while it is off the icons keep their colours. A scan, seek or lookup has a page beside its icon. The page shows in grey while the operator is working inside a GetRow call, but not at the call itself or its return, and flashes blue when the operator gets a page from the buffer pool. Each row the operator reads draws a line across the page where the row's slot sits, near the top for the first slot and near the bottom for the last. An IAM page shows an **I** and a PFS page a **P**, in the colours of the **Read** track's **IAM Read** and **PFS Read** ticks.

Under the operator's name, the last page it got from the buffer pool up to the playhead shows as a link, such as `(1:200)`. Once the operator reads a row on that page, the link shows the row instead, as File Id:Page Id:Slot, such as `(1:200:5)`. Click it to open the page, at the row's slot, in a tab that moves with the operator: it follows the operator from page to page and row to row as the playhead moves. Any other tab showing the page the operator is on selects the operator's row too, in the hex view and the slot list, when that row changes. The link stays the same size as the plan zooms, and is hidden when the plan is zoomed out so far that the operator names are too small to read. Below it, each [watch](/docs/user-guide/query/TraceTimeline#watches) on the operator shows its label and its value at the playhead, such as a row count, updating as the playhead moves.

A badge at the top right of an icon counts what a track's **Counter** rules have seen on the operator up to the playhead, and its tooltip lists every count. The predefined **GetRow/GetBatch** track counts the rows or batches each operator has returned so far, and the statement at the top of the plan counts the rows returned to the client. Only the statement shows its badge to start with. **Show Counter** in an operator's right-click menu turns its badge on.

Where an operator runs in a different execution mode from the operator above it, a **Batch To Row Adapter** or **Row To Batch Adapter** is drawn between them. SQL Server converts between the two modes there, and the plan XML does not list the converter, so the plan works it out from each operator's execution mode. A converter has no cost and can't be selected.

In a row mode plan a Compute Scalar only defines an expression. Nothing runs at that point in the plan, so a [Full Trace](/docs/user-guide/query/FullTrace) run leaves it off. An operator that outputs the computed value has a small calculator to the left of its icon instead, with the expression in its tooltip, and the calculator lights up while the expression runs. That's the statement when the row is sent to the client, or an operator that stores the value with its rows and returns it, such as a Sort. An operator that only reads the value, such as a Filter, a join on the expression or an aggregate over it, has no calculator. A batch mode Compute Scalar is a real operator, so it stays on the plan, with the iterator lines running straight through it and the calculator to the left of its own icon. It runs once for each batch, when the operator above asks for its data. In [Guide Mode](#guide-mode) each evaluation is an **Evaluate** step under the heading of the operator that needed it, showing the expression in place of a description.

Selecting an operator (on the plan, the Timeline's Plan band, or the Events pane) outlines its icon and, for a [Full Trace](/docs/user-guide/query/FullTrace) run, focuses the [Call Tree](/docs/user-guide/query/CallStack) on that operator's frames. A Full Trace run leaves the outline off, so it does not compete with the parts of the icon the playhead lights.

**Double-click** an operator to select it and open its **Properties**. **Right-click** an operator for:

- **Open Index:** and the index's name - opens the index in the [Index View](/docs/user-guide/index-view), linked to the replay, or a columnstore index in the [Columnstore Viewer](/docs/user-guide/columnstore)
- **Simulate** - steps through the operator and everything beneath it in the [Simulation](/docs/user-guide/query/Simulation) pane
- **Call Tree** and **Properties** - open those panes for the operator
- **Show Counter** - for a [Full Trace](/docs/user-guide/query/FullTrace) run, shows or hides the operator's counter badge. The statement's is on to start with and every other operator's is off

## Guide Mode

**Guide Mode**, on the [Trace menu](/docs/user-guide/query#trace-menu), walks through a [Full Trace](/docs/user-guide/query/FullTrace) run on the Execution Plan. Turning it on also turns on **Record Full Trace**, with the same dialogs, and sets the layout to the SQL Editor, the Trace Timeline and the Execution Plan as tabs, keeping the tab you were on. When a Full Trace has finished loading it switches to the Execution Plan, zoomed to fit the pane. The Trace Timeline shows only its **Operators** pane. The layout stays while it is on, run after run, and turning it off puts the previous layout and the Trace Timeline's panes back.

**Previous** and **Next** on the command bar of the **Steps** panel under the plan move the playhead to the previous or next step. Every tick on the [operator tracks](/docs/user-guide/query/TraceTimeline#operator-tracks) that are turned on is a step, at the start of its call. A rule with a return description adds a second step at the end of each call, so a GetRow call is two steps, such as "Top calls `GetRow` from Table Scan" and then "`GetRow` returns a row from Table Scan to Top". The plan lights up as it would at that point on the Trace Timeline, and an orange arrow above an operator points at the one heading the current step. For a `GetRow` or `GetBatch` step the arrow sits above the line between the two operators instead, pointing the way the call or its return is going. The panel under the plan lists every step, in order, with the current one at the top, marked by an orange arrow and shown on white, and the others in grey. Steps in a row on the same operator sit under one header with the operator's icon and name, which stays at the top of the panel as you scroll and is grey unless it holds the current step. Each step shows the rule's title in bold and its description, or its return description for a return, both as Markdown. Steps are indented by how deep the call is, so the steps inside a `GetRow` or `GetBatch` sit under it, ending with its return. The chevron on a call hides or shows what is inside it. **Next**, **Previous** and **Play** step over a collapsed call, and moving to a step inside one any other way expands it. Click a step to move the playhead to it. A page in a step is a link that opens the page, at the row when the step read one. Code in the text, such as `GetRow`, is drawn like the call's block on the Trace Timeline, in the colour of its category. Drag the line above the panel to resize it. **Steps** on the Execution Plan's tab shows or hides the panel, and the **X** in the panel's header closes it. A slider under its command bar shows how far through the steps the current one is, and dragging it moves through them.

A **Seek** step shows the one range of its **Seek Predicates** that the seek is working on. On the inner side of a Nested Loops join, when the key columns are integers taken from the outer row, it shows the values being looked up, such as `Id = 5`. The pages it reads on the way down the index and its searches of those pages are nested under that step, and the step stays in view under the operator heading while you scroll through them.

While Guide Mode is on, **Play**, **Previous** and **Next** on the Query tab's command bar step through the same steps, with or without the Trace Timeline open, and the Trace Timeline's step menu is set to **Tracks**. **Play** holds on each step long enough to read the plan, for less time at a faster playback speed. Turning Guide Mode off puts the step menu back.

**Previous** and **Next** on the panel's command bar are split buttons. Clicking one moves a single step, into a phase and through the steps inside it. Its menu also has **Previous Phase** and **Next Phase**, which go to the start or the end of a rule marked as a **Phase**, such as the **Hash Table** and **Sort** tracks' **Build**, stepping over the steps inside. **Previous Operator** and **Next Operator** go to the first step under the previous or next operator heading in the panel. **Play** moves through the steps on its own, as **Play** on the Query tab's command bar does, and **Pause** stops it. **Details** shows the longer explanation of the steps that have one.

Describe the steps in the Operator Tracks tab, such as the predefined **Row Access** rule's `Read row data at Slot {Slot} on Page {Page}`.

## Command bar

- **Annotations** - not available for a Full Trace. Adds badges to the operators something notable applies to. For a columnstore scan that is **Aggregate Pushdown** and **Local Aggregation**, **Compressed Filter** where a predicate was evaluated without decoding the segment, **Predicate Pushdown**, **Segment Elimination**, **Global Dictionary**, **Deep Data** for values too wide for a vector slot,, **Fast Comparison**, and **SIMD** with the instruction set it used. Elsewhere, **Row Goal**, **Row Mode** for a row mode operator over batch mode input, **Over Grant** where an operator used more memory than it was granted, and **Untranslated Predicate** where the trace cannot evaluate a predicate. The toggle is remembered between sessions
- **Properties** - opens a pane beside the plan with the selected operator's properties from the plan, grouped - **Operator**, **Optimizer**, **Storage**, **Predicates**, a group for the operator's own work such as **Hash** or **Nested Loops**, **I/O Statistics**, **Memory Grant** where it had one, **Event Statistics**, **Defined Values** and **Output Columns**. The button on its header docks it to the right or the bottom
