# Trace Timeline

The Trace Timeline draws every call recorded by a [Full Trace](/docs/user-guide/query/FullTrace) - one lane per thread, one bar per call, each call nested beneath the call that made it. The bars use the [Call Tree](/docs/user-guide/query/CallStack)'s category colours.

The Call Tree merges every call down the same path into one row with a count. The Trace Timeline keeps each call apart, in the order it happened, so a scan's `GetRow` calls show as a run of short bars, one per row, and a function called once for a long time as a single wide one. It takes the Timeline's place while **Record Full Trace** is on, and the **Trace Timeline** item on the View menu, enabled only then, brings it back if it is closed.

## Reading the chart

From top to bottom:

- **The ruler** - how far through the recording, in trace positions or instructions - see [Position and instructions](#position-and-instructions). Click it to put down the [playhead](#playhead)
- **The Operators pane** - with **Operators** on, a row per plan operator - see [Operators](#operators)
- **The Memory History lane** - with **Memory** on, the memory blocks the query wrote to and the writes to each
- **A lane per thread** - headed **Thread** and the operating system thread id
- **The memory band** - with a view chosen under **View > Flame Chart > Memory**, the memory allocated and in use along the bottom - see [Memory](#memory)

**Operators**, **Memory** and **Calls** on the tab strip show and hide the Operators pane, the Memory History lane and the thread lanes. The last of the three left on cannot be turned off, and the ones you leave on are remembered between sessions. **View > Flame Chart > Highlight Regions** shades the stretches of the lanes where the query was compiled, started and shut down, as **Compilation**, **Setup** and **Shutdown**, each with its own toggle. **View > Memory History > Writes** and **Reads**, also on the lane's right-click menu, choose what the lane marks: writes, which are on by default, reads, or both. A read is marked once for each call that read a block, at the position of its first read and across the bytes it read, in a lighter shade of the reading call's category colour. The lane also holds the objects a function keeps on its own stack once it hands them to another function, as the object a member function is called on, or as an argument or return value declared as a pointer to a class. Such an object is read as it is handed over and again when that call returns, so its changes are what was different at each handover, credited to the function handing it over or to the function it was handed to. A function's local is one object however often the function runs, and each call is an instance of it, so the lane draws a bar for each call and its changes run on from one call to the next. Clicking one moves the playhead there and opens the block. **View > Memory History > Size to Fit**, on by default, squeezes every block into the lane. Turn it off to draw the blocks at their relative sizes, with a scroll bar always on the right of the lane, and the mouse wheel over the lane scrolls through them. **View > Memory History > Call Highlight Hover** dims every call except the ones that wrote to the block under the pointer while you hover over the Memory History lane. **View > Memory History > Latching** and **BUF** are covered in [Buffer latches](#buffer-latches). **View > Reset Layout** puts the pane heights back and docks the Call Stack and memory tabs beneath the chart again. Right-clicking any of the three areas offers the same three toggles, with the only area still showing greyed out, then that area's own view settings and **Call Stack**, so the View menu's settings are a click away wherever you are. Right-clicking a block in the Memory History lane also offers **Open Reference Graph** for that block, covered under [Call Stack](#call-stack).

In a lane, each call is a bar running from where it started to where it ended. The calls it made sit directly beneath it, inside its width, so the outermost call is at the top of the lane and each row down is one level deeper in the stack. That is the reverse of a classic flame graph, which grows upwards, but it reads the same way as the Call Tree. A bar is coloured by its function's category and labelled with the function's name once it is wide enough to read.

- **A wide bar** - a call that ran for a long stretch, and on the Instructions axis, one that executed a lot of code
- **A run of thin bars** - the same function called over and over, such as a scan's `GetRow` once per row
- **A gap beneath a bar** - the call working in its own code rather than in a call it made. Extended Events and tracing code is left out of the chart, and where it took up a noticeable stretch of a thread that stretch is cut out too, so the calls either side of it close up. On the **Position** axis a stretch is only cut when no other thread started or finished a call during it. A faint dotted line on the ruler marks each place a stretch was cut
- **A pale strip** - calls too narrow to draw one by one, merged into a single strip. Zoom in to pull them apart

## Position and instructions

TTD has no clock. A recording is a sequence of positions - a sequence number shared by every thread, plus the number of instructions the thread has executed since - so the ruler is never in milliseconds. **View > Scale** chooses what a bar's width means:

- **Position** - the default. Width is the span of trace positions a call covered. Positions are shared by every thread, so the lanes line up against each other and parallel workers can be compared. A position moves on by one whole step at each point where a thread synchronises with another or leaves the recorded code, however many instructions came before it. So short calls that cross one of those points come out about the same width, and calls that stay inside the recorded code without crossing one are thin.
- **Instructions** - width is the number of x64 machine instructions the call executed, including the calls beneath it, which is the closest the recording has to how long a call took. Only the storage engine and query processor are recorded, so time spent in SQLOS or Windows - allocating memory, waiting, reading from disk - adds next to nothing. Each thread counts its own instructions from zero, so every lane starts at the left and the lanes do not line up.

## Moving around

- **Mouse wheel** zooms in and out at the pointer
- **Shift + mouse wheel**, or a horizontal wheel, pans sideways
- **Ctrl + mouse wheel** scrolls through the threads
- With **Size to Fit** off, the Memory History lane keeps a scroll bar on its right, the **mouse wheel** over the lane scrolls through its blocks, and **Ctrl + mouse wheel** zooms there instead
- **Drag** pans sideways, and a **middle-button drag** pans in both directions
- **Shift + drag** draws a rectangle and zooms to it
- **Shift + click** a bar to scope the chart to its function, or empty space to go back to the whole recording
- **Double-click** a bar to zoom to it, or empty space to clear the selected call and operator
- **Click a thread's name** in its header to expand that thread and collapse the others to their headers, and click it again to show them all. Clicking anywhere else along a header puts the [playhead](#playhead) there
- **Mouse back and forward buttons**, anywhere in the Trace Timeline, go back and forward through the places the chart has jumped to, such as a clicked call, a followed link, **Zoom to** or a search match. Scrubbing the playhead and **Play** are not recorded

The lanes shrink to fit every thread into the pane, and a call's name appears once there is room to read it - zoom in, or click a thread's name to give it the whole pane, to see more of them.

## Right-click menu

Right-clicking a bar gives:

- **Zoom to** - only over a call. Zooms to the call under the pointer, as double-clicking it does, scrolls its thread into view and selects it
- **Zoom to 100%** - wherever you right-click. Zooms back out to the whole recording
- **Scope** - scopes the chart to the call's function, as **Shift + click** does - see [Scoping to a function](#scoping-to-a-function)
- **Clear Scope** - only while the chart is scoped, wherever you right-click. Goes back to the whole recording
- **Open Call Tree** - opens the [Call Tree](/docs/user-guide/query/CallStack) at the call's frame, with the call selected in the [Arguments](/docs/user-guide/query/CallStack#arguments) tab. Right-clicking empty space just opens the pane, and if it is already open its tab is selected

## Selecting a call

**Click** a bar to select the call. It is outlined, the Call Tree goes to its frame, and the [Arguments](/docs/user-guide/query/CallStack#arguments) tab follows with that call selected. Nothing is dimmed, so the rest of the chart stays readable. Click the selected bar again, or the background, to deselect.

With a call selected, the arrow keys move the selection:

- **Up** - the call that made it
- **Down** - back down the [call stack](#call-stack), or from its innermost call to the first call it made
- **Left** and **Right** - the previous or next call at the same depth on its thread, even when a different call made it

With **View > Auto-Zoom** on, the chart zooms to fit the selected call whenever the selection changes, whether it was clicked here or selected in the Call Tree or **Arguments**.

Hovering over a bar describes the call:

- The function and its category
- **Thread**, **Call** and **Depth** - the thread it ran on, which call of the function it was, and how deep in the stack
- **Instructions** - how many instructions it executed
- **Position** - the trace positions it started and ended at
- **Allocated**, **Freed** and **Retained At Return** - for a call that allocated memory, how much and in how many allocations, how much it freed, and how much was still held when it returned
- **Started Before The Recorded Call** - the call was already running when its part of the recording began, so its start is not known
- **Did Not Return** - the call had not returned when the recording stopped, or the recording lost it in a gap

## Following the Call Tree

Choosing a call in the [Arguments](/docs/user-guide/query/CallStack#arguments) tab selects it in the chart, outlined as if its bar had been clicked, and scrolls it into view. If the chart is scoped somewhere that call is not, it goes back to the whole recording to show it. A frame in the Call Tree stands for every call made down that path, so selecting a frame there does not pick a call, and the chart is left as it is.

<!-- Screenshot: one call chosen in the Arguments tab, outlined in the Trace Timeline -->

The Call Tree's [category filter](/docs/user-guide/query/CallStack#filtering-by-category) applies here as well. A hidden category's calls are taken out and the calls they made move up into their place, so a category you have kept is never lost beneath one you have hidden. A category hidden with **Hide With Callees** takes everything beneath its calls with it. The Memory History lane follows the filter too. A block is left out when every read and write to it was made by a call the filter has taken out.

## Scoping to a function

**Shift + click** a bar, or right-click it and choose **Scope**, to scope the chart to its function. Only that function's calls and everything beneath them are drawn, zoomed to fit, so a function called from all over the query can be looked at on its own. Depths count from its outermost call, so a function that calls itself does not draw over itself. A thread that never ran the function - a parallel worker never runs beneath the coordinator's frames - shows what it was doing over the same trace positions instead.

**Shift + click** empty space, or choose **Clear Scope** from the right-click menu, to go back to the whole recording.

## Search

The **Search** toggle opens a bar above the chart, and **Ctrl+F** anywhere in the Trace Timeline opens it with the cursor in the box. The strip beneath the ruler, where the playhead's triangle sits, is marked in yellow wherever a call whose function name matches every word typed runs, on any thread, and a yellow bar down the left edge of the Memory History lane marks the rows of each block whose name matches them. A word matches when the name contains it or has its letters in the same order, so `qshgr` finds `CQScanHash::GetRow`. Zoomed in, only the blocks alive in the part of the recording on screen are marked. Clicking a yellow bar zooms to what it marks at that point. Over a single call the chart zooms to that call and selects it, and over memory it zooms to the time the blocks there are alive. Hovering over a yellow bar reads **Search Results**. The number of matching calls and blocks shows beside the box, or **No Results** when nothing matches. **Escape** closes it. Right-clicking a function or type name in the Call Stack, its details, the memory **Details** or a call on the chart gives **Search**, which opens the bar with that name in it.

**Call** and **Memory** after the box choose what is searched, and both start on.
- **Call** matches calls by function name. A page or row typed as `1:2676` or `1:2676:3`, a row id in hex, or `rg:1 col:2` for columnstore matches the calls that read it instead, the same as the Call Tree's search.
- **Memory** matches Memory History blocks by name. An address typed with `0x` matches the blocks that contain it, and a page matches the BUFs that held it at any point. While it matches any blocks, the Memory History lane shows only those blocks. With nothing typed, or no block matching, the lane shows every block, objects on the heap first and objects on the stack below them.

As you type, a list under the box shows the matching function names with how many calls each made, then the matching memory blocks with their address and size, each in alphabetical order. Choosing a function or a block puts its name in the box, where it can be edited like anything typed. **Open** at the right of a block opens it as a memory tab.

The arrows after the box move to the previous or next match in time and bring it into view, and are greyed out while nothing matches. A matching call is selected, and for a matching block the playhead moves to where it was created. **Enter** in the box moves to the next match and **Shift+Enter** to the previous one. Stepping starts from the selected call, or from the playhead when nothing is selected.

The filter button beside the **Search** toggle opens the same category badges as the Call Tree's [category filter](/docs/user-guide/query/CallStack#filtering-by-category), beneath the search bar. They are one setting, so hiding a category here hides it in the Call Tree too.

## Operators

**Operators** on the tab strip adds a pane above the threads, with a row per plan operator in the same order and colours as the Timeline's Plan band. A Batch To Row adapter between batch and row mode operators is grey. Each row runs from the operator's first call to its last. The stretches where one of its methods was on the stack are drawn in full colour and the rest shaded, and an operator that ran on several threads gets a track per thread. Either side of that, a fainter bar shows how long the operator's iterator existed. It starts at the iterator's constructor, or for a batch mode operator the call that built it, and ends with the query's `CQueryScan::DestroyQuery`, where SQL Server frees all of a query's iterators together. When the recording started after an iterator was built, or stopped before the query was torn down, the fainter bar runs to the edge of the recording.

The top row is the statement, such as **SELECT**, in grey. Its **GetRow Returns** strip has a tick for each call the statement made to the plan's top operator, with a line down to it, so its **Returned** ticks are the rows the query returned.

This shows something the lanes cannot. An operator is only on a thread's stack while one of its methods runs, so a Hash Match sits beside its scans in the lanes rather than above them - but its iterator object exists from the moment it is built until the query is torn down, and does its work from its first call to its last. The Operators pane draws both.

- **Drag** the splitter under the pane to make its rows taller
- **Drag** the bottom edge of a row to resize that row alone, and the inner edge of a strip to resize that track's strip on every operator. The sizes last until another trace is opened
- **Click** an operator to select it in the [Execution Plan](/docs/user-guide/query/ExecutionPlan). While [Call Stack](#call-stack) is off, everything except its calls and the calls beneath them is dimmed
- **Double-click** an operator to zoom to its lifetime
- Hovering over an operator shows its thread, how many times each of its methods was called, its instructions and positions, the share of its lifetime spent inside its calls (child operators included) and its peak memory in use

## Operator tracks

Each operator bar can carry thin strips of ticks, one strip per track. A tick is one call, drawn as a faint bar across the call with a solid tick at its end. A strip only appears on an operator that has ticks on it. Every operator keeps the same room for its name, so an operator with more strips is drawn taller and the others give up the height for it.

Every track is made of rules. A rule picks out the calls to tick and gives them a label and a colour. Rules that share a track name make one track, each rule one kind of tick on it, so a track can show several kinds of call side by side. These tracks come predefined:

- **GetRow/GetBatch** - along the top, a tick for every `GetRow` or `GetBatch` call the operator answered, coloured by what happened to the row (see below)
- **Read** - along the bottom, the operator's requests to the buffer pool, page reads and read-aheads. A request for an IAM or a PFS page has its own colour, as an **IAM Read** or a **PFS Read**
- **Evaluations** - above the reads, the predicates the operator evaluated, coloured by whether they were true, false or NULL. A Stream Aggregate's comparison of each row with its current group is a **No Change** tick when the row joins the group, which lights the operator's sum symbols green as the row is added to its aggregates, and a **Change** tick when the row starts a new group and the finished group is returned
- **Page** - the operator's reads of buffer pool pages. A **Row Access** tick is a row the operator read, with the page and slot, coloured by the category of the function that read the row. Reading a slot's entry in the page's slot array is not a row access, only reading the row itself. A row read while a seek searches a page for its key, under `PageRef::SearchPage`, is a **Search Page** tick instead. When the search reads the row at the slot `PageRef::SearchPage` returns, that read is a **Found** tick. Only data and index pages hold rows, so the reads an allocation scan makes of the IAM and PFS pages are not row accesses. A **Page Header Access** tick is a read of the 96 byte header of a page, on any type of page. Reads of the same header within one call are one tick, and a read after the operator has read a row or got a page is a new tick. The tick's tooltip names the fields read, such as **Log Sequence Number** or **Slot Count**, with the names the Page Viewer uses
- **Seek** - each b-tree seek, with the root, intermediate and leaf pages it went through. In the Execution Plan the seek's icon lights its root, intermediate and leaf node in turn
- **Open** - each operator from its first call, its Open, to its last, when it is closed. In the [Execution Plan](/docs/user-guide/query/ExecutionPlan) the operator's icon is in colour for as long as the operator is open, and grey otherwise
- **Hash Table** - each hash join's **Build** of its hash table, each **Insert** of a build row into the table, and each probe row it looked up in it, as a **Hit** when the lookup found a build row and a **Miss** when it did not
- **Hash Aggregate** - a batch mode Hash Match (Aggregate): its **Build** from its input batches, each **Push Batch** into its local hash table with the **Look Up** of the group keys and the **Aggregate** of the values, its **Merge** of the local groups into the global hash table through **Repartition** and **Partition Page**, and each **Output Batch** it fills with finished groups
- **Statement** - the statement's **Initialise**, which sets up the query and asks for its first row before the loop that fetches the rest
- **Compute Scalar** - each time a Compute Scalar's expression runs, on the operator that needed it, such as **Row Send**, **Filter**, **Sort**, **Hash Build**, **Hash Probe**, **Stream Aggregate**, **Seek Key**, **Startup** for a runtime constant, and **Batch** for a batch mode Compute Scalar
- **Sort** - each sort's **Build** of its sort table from its input, each **Push Row** of an input row into the table during the build, and each **Sorted Row** it read back from the table in order

Each track has a toggle under **View > Operators**, and under **Tracks (All)** in the Operators pane's right-click menu. Turning a built-in track off is remembered between sessions. The **Open** track starts off. Right-clicking an operator also gives **Tracks (Operator)**, which turns a track off or on for that operator alone, until the next run.

You can add your own rules for any function. **Add to Operators**, in the right-click menu of any call in the chart, adds one for that call's function. **Custom...**, under **View > Operators** or in the pane's right-click menu, adds one for a function you pick. A rule ticks the operator each call was made inside. A track you start has a lighter strip so it stands apart from the predefined tracks. A call made outside every operator has no tick. The dialog sets:

- **Function** - the function whose calls are ticked. Type part of its name to pick it from the functions in the trace
- **Track** - the track's name in the **View** menu and its tooltips, the function's name to start with. Pick an existing track to add the rule to it
- **Label** - what this rule's ticks are called on the track, in its tooltips and its counts. The function's name when left empty
- **Title** - the name of each of the rule's [Guide Mode](/docs/user-guide/query/ExecutionPlan#guide-mode) steps, such as `Evaluate Expression` for the **Evaluations** rules, whose labels are `True`, `False` and `NULL`. The label when left empty
- **Description** - what happens at each tick, added to its tooltip under its label and shown at its Guide Mode step. It is Markdown, so `` `GetRow` `` shows as code in Guide Mode. The label and the description can hold placeholders, filled in for each tick: Put `<Predicate>{ExecutionPlan.Predicate}</Predicate>` in it to show a value from the operator's **Properties** at its Guide Mode step, under the description and formatted the way predicates are. `{ExecutionPlan.Name}` can be any property there, written without its spaces, such as `{ExecutionPlan.ProbeResidual}`. `{ExecutionPlan.CurrentRange}` is the one range of a seek's **Seek Predicates** that the seek is working on at that tick, with the actual values when the key columns are integers taken from the outer row of a Nested Loops join. An operator without that property shows nothing.
  - `{OperatorName}` - the operator the tick is on
  - `{ParentOperatorName}` - the operator that called it, or its parent in the plan
  - `{Function}` - the function the tick is a call to
  - `{Page}` - the page the tick read or got from the buffer pool, such as `(1:2672)`. In Guide Mode it is a link that opens the page, at the row when the tick read one
  - `{Slot}` - the slot of the row a **Row Access** tick read
  - `{HeaderField}` - the page header fields a **Page Header Access** tick read, separated by commas. In backticks each field is shown as code
  - `{Result}` - the rule's label, such as `True` or `False`. In a Guide Mode step, code in a description that uses it takes the rule's colour, so `` `{Result}` `` matches the colour of its tick
  - `{Partition}` and `{Bucket}` - where a **Hash Table** **Insert**, **Hit** or **Miss** went in the hash table, worked out from the row's hash. They need Memory History. In Guide Mode the bucket is a link that opens the hash join's [Hash Table](#hash-table) at that bucket

  A placeholder the tick has no value for shows as `?`. Every predefined rule has a description, such as **Row Access**'s `Read row data at Slot {Slot} on Page {Page}`
- **Details** - a longer explanation of why it happens, added to the tick's tooltip below its description and to its Guide Mode step. It can hold the same placeholders as the description
- **Return Description** - what happens at the end of each call, for a second Guide Mode step at the return. The predefined **GetRow/GetBatch** rules describe the call as `` {ParentOperatorName} calls `GetRow` from {OperatorName} ``, and the return by what happened to the row, such as `` `GetRow` returns a row from {OperatorName} to {ParentOperatorName} `` for **Returned**
- **Plan Part** - a part of the operator's icon in the [Execution Plan](/docs/user-guide/query/ExecutionPlan) to light in the rule's colour while the playhead is inside one of its calls, such as `Root Node`. `Active` is the whole icon in its own colours, and while a rule bound to it is turned on, the icons are grey until it lights them. Every icon names its parts the same way, so each b-tree icon has a `Root Node`, an `Intermediate Node` and `Leaf Node 1`, `Leaf Node 2` and so on from left to right. A part named without its number, such as `Leaf Node`, lights every part of that kind. Put an operator in front, such as `Index Seek.Root Node`, to light that operator's icon only
- **Counter** - counts the rule's ticks on the operator's icon in the Execution Plan, each one once its call has returned at the playhead. The counter rules of a track add up to one count, and the predefined **GetRow/GetBatch** track counts the rows each operator returned this way
- **Phase** - [Guide Mode](/docs/user-guide/query/ExecutionPlan#guide-mode)'s **Next Phase** and **Previous Phase** stop at the start and the end of each of the rule's ticks, stepping over the steps inside. The predefined **Hash Table**, **Hash Aggregate** and **Sort** tracks' **Build** rules are phases, and so are **Hash Aggregate**'s **Merge** and **Statement**'s **Initialise**
- **Plan Default** - every tick of the rule is a [Guide Mode](/docs/user-guide/query/ExecutionPlan#guide-mode) step, whether or not its track is turned on. It starts on. When it is off the rule is listed under **Additional Steps** on the Execution Plan's [View menu](/docs/user-guide/query/ExecutionPlan#view-menu). The predefined **Page Header Access** and **Open** rules are not plan defaults
- **Colour** - the colour of its ticks, the function's category colour to start with. **Category Colour** colours each tick by the category of the function that made it instead, which suits a rule that matches several functions
- **Background** - the colour behind the track's strip, turned on with **Background Colour**. Lower its alpha to let the operator's colour show through. Without one the strip is a shade of the operator's colour. A track takes it from its first rule, and the predefined **Page** track has a translucent white background
- **Height** and **Width** - how tall the strip is and how wide each tick is, as a multiple of the predefined tracks, so **1.5** is half as tall or wide again. A track takes them from its first rule
- **Conditions** - which calls get a tick. A call gets a tick only when every condition matches, and with no conditions every call does. Each condition is one of:
  - **An argument or the return value**, an operator and a value. A number, such as `0`, `-1` or `0x1F`, is compared with the argument's value at its own size. Anything else is compared with the value as the **Arguments** table shows it, such as `true`, a page like `1:1536` or `NULL`.
  - **Called By** a function, anywhere up the call stack, or **Called Directly By** a function, the call's immediate caller. For a **Row Access**, **Seek** or **Page Fetch** rule, **Called By** also matches a tick made inside the function itself. The value is a function name, matched the same way as in the Call Tree's search, so `*Scan*::GetRow` matches any scan's `GetRow` and `sqlmin!` limits it to one module. Use **!=** to tick calls that were not made from it.
  - **Operator** - the operator the tick lands on, such as `Filter` or `Table Scan (Node 3)`.

For example, `CEsExec::FastCompare1` with **Called By** `CQScanTableScanNew::GetRow` ticks the predicates a scan evaluated itself, while **Operator** `Filter` ticks only a Filter's. A scan below a Filter is also called by the Filter, so **Called By** the Filter's `GetRow` would include the scan's too. Use **Called Directly By** or **Operator** to pick out the Filter alone.

The same function can be added more than once, such as one rule for `GetRow` calls that returned a row and another for those that did not, both on one track in two colours. A call that two rules of the same track pick out gets one tick, from the rule that comes first. The rules you add are saved, and every trace you open in this or a later session shows them. Turning a track off in the **View** menu hides it like a predefined one.

**Operator Tracks**, on the Trace menu, opens a tab listing every rule, predefined and added, with its track, label, title, function, conditions, description, return description, colour, background, height and width. **Add** on its command bar opens the same dialog. **Edit** changes a rule, and **Delete** removes a rule you added. A predefined rule cannot be deleted, so turn its track off in the **View** menu to hide it. A predefined rule you change comes back in the next session, or straight away with **Reset Predefined**. **Clear Added** removes every rule you added. **Export** saves every rule to a file as it stands, predefined and added, so a predefined rule you have changed can be copied out. **Import** loads the rules in a file as rules you added, so importing a full export adds a second copy of each predefined rule.

- Hovering over a strip names it in a label at the left of the operator, beneath a strip along the top and above one along the bottom, and shows how many ticks of each kind the operator has on that thread
- Hovering over a tick outlines its call in red in the lanes below, and shows what kind of tick it is, its rule's description, its function, thread and position
- **Click** a tick to select its call in the chart
- **Double-click** a tick to zoom to it

### Watches

A watch follows a value inside each operator's object, such as a row counter, as the query runs. **Add Watch** in the Operator Tracks tab's command bar adds one. It needs a Full Trace recorded with **Memory History**, which keeps every write to the objects the query made.

- **Class** - the class of the operator's object, such as `CQScanTopNew`. Type part of it to pick one of the classes in the trace
- **Offset** - where the value starts in the object, in bytes, as decimal or `0x` hex
- **Length** - how many bytes the value takes
- **Data Type** - how to show the value, such as `Int` or `SmallInt`, or **Hex** for its bytes as they are in memory
- **Label** - the name shown beside the value

On the track, each stretch of the strip is one value, from the write that set it to the next write that changed it. The value is written in the stretch when it is wide enough, and hovering over it shows the value and where it is in the object. With **View > Watches** turned on in the [Execution Plan](/docs/user-guide/query/ExecutionPlan), the label and value at the playhead are a row in the table below the operator. A watch is not a [Guide Mode](/docs/user-guide/query/ExecutionPlan#guide-mode) step.

The predefined **Rows Remaining** watch, on the **Watches** track, follows how many rows a **Top** still has to return. It starts at the Top's row count when the operator opens, and goes down by one with each row.

### GetRow returns

A tick is a call to the operator's `GetRow`, or `BpGetNextBatch` for a batch mode operator. It ends at the return and is coloured by what happened to the row. **Returned** rows went on to the operator that asked for them, including every row a blocking operator reads before it returns its first, such as a Sort, an Eager Spool or a Hash Match building its hash table. **Skipped** rows were taken by the operator that asked for them without it returning a row before it asked again, such as the rows a Stream Aggregate folds into a group. **Rejected** rows failed a Filter. **End** is the call that reported there were no more rows.

A line runs from each call up to the operator that made it. The dotted line is the call, in the track's colour. The solid line is the return, in the colour of the call's marker, and meets the marker's edge. The lines are drawn only once the calls are wide enough to tell apart.

### Reads

A call to `BPool::Get` asks for a single page. A call to `BPool::ReadAhead` asks for a run of pages ahead of the scan. Each read is drawn in the Buffer Pool category's colour, and its tooltip shows the page, or the first page and page count of a read ahead. Pages already in memory and pages read from disk are drawn the same way. The calls beneath a read in the lanes below show which it was, such as `BPool::GetFromDisk` when the page had to be read. Reads made outside every operator, such as metadata lookups while the query is set up, are not shown.

### Evaluations

SQL Server evaluates a predicate with `CEsExec::FastCompare` or `CEsExec::GeneralEval`, which write the result into a value passed in by the caller. Each tick is coloured by that result - green for true, red for false and grey for NULL, where a comparison against a NULL could not be decided.

A scan with a predicate pushed down into it evaluates every row it reads but only passes up the rows that match, so the strip shows the rows it skipped as well as the ones it returned. Comparisons an operator makes for its own work are included too, such as a Stream Aggregate checking whether a row starts a new group. Evaluations that produce a value rather than true, false or NULL are not shown, and neither are the three-way comparisons a Merge Join makes between its inputs.

## Memory

**View > Flame Chart > Memory** shows where the query allocated memory, as **Allocated** or **In Use**, with **None** turning it off:

- **The memory band** - along the bottom of the chart, **Allocated** is the memory allocated in each sliver of the recording, and **In Use** is the memory allocated and not yet freed, with its peak in the label. When the plan had a memory grant, the grant is drawn as a box labelled **Granted** and the line becomes **Grant In Use**, counting only the query's workspace memory so the two compare like for like. The band needs the Position axis, since each thread counts its instructions separately and they cannot be added together.
- **Raised calls** - the calls rise off the chart in 3D. A dropdown above the ruler picks **Memory: Allocated**, which raises each call by the memory it allocated itself, or **Memory: In Use**, which raises a surface along each call showing what it had allocated and not yet freed as it ran. Hover over a raised call to see its size, and drag one to change the angle and depth of the extrusion.

![Memory: In Use - a surface along each call showing the memory it held as it ran](/docs/user-guide/images/flame-chart-memory-in-use.png)

### Buffer latches

**Latching** in the Memory History lane's right-click menu, or under **View > Memory History**, adds a thin row along the bottom of the lane, under a divider, marking every change to the latch of a buffer pool page the query fetched. Each mark is coloured by the latch after the change: blue while it is held shared, red while it is held exclusively, orange while threads are waiting for it, and grey once it is released. Hovering over a mark names the page, such as **BUF (1:43)**, and the latch. Clicking it moves the playhead there and opens the page's BUF, the buffer pool's descriptor for the page, as a memory tab. Latches taken by other threads show on the Position axis only, because the Instructions axis counts the query's own threads. The BUFs themselves are left out of the lane's blocks, and **BUF** on the same menus adds them back. Both settings are remembered between sessions.

### Hash Table

A row mode hash join's hash table opens as a tab of its own. The bucket link on a **Hash Insert** or **Hash Probe** step in [Guide Mode](/docs/user-guide/query/ExecutionPlan#guide-mode) opens it below the Execution Plan, at that bucket. In any Full Trace, with or without Guide Mode, **Hash Table** on a Hash Match's right-click menu in the Execution Plan opens it below the plan too, and **Open Hash Table** on the hash join's right-click menu among the Trace Timeline's operators opens it on the Trace Timeline. So does **Open Hash Table** on a call to the partition group or one of its partitions in the chart, at the bucket the call used when it is an insert or a lookup. A memory tab on any part of a hash table has **Hash Table**, the partition group's address and which part it is, such as **Partition 3 Item Page**, along its top, and **Open Hash Table** on the tab's right-click menu. The parts run from the partition group, its partitions, directories and pages of pointers, to the item, overflow and workfile pages, and include the objects a partition links to: its workfile rowset, and the bitmap and its pages. Either opens the hash table on the Trace Timeline beside the memory tabs, with that part selected. The **Memory** pane of the [Trace Summary](#trace-summary) offers **Open Hash Table** on the right-click menu of every object in a hash table too. A hash table already open in one place is brought forward there. It follows the playhead wherever it is. The tab has three parts side by side: a tree of the table's structure, the bytes of the part selected in the tree, and the detail for that part.

The tree starts at **Hash Table**, the Hash Match operator itself, with **Memory** first under it and then the partition groups it created under **Build Side** and **Probe Side**. Each side has a **Partition Group**, the `CHashWorkfilePartitionGroup` that side's rows are partitioned into, a **Worktable Group**, a `CHashWorktablePartitionGroup` that sets up a worktable in tempdb, and a **Rebuild Group**. After a spill, a join rebuilds its table in a rebuild group, from whichever side's spilled partitions are smaller. A hash aggregate has only a build side, with a partition group and a worktable group. The group marked **In Use** is the one the operator is filling or probing. A group that the run never inserts into or looks up in is greyed out. Under a group, **Accessors** lists the columns of the rows it stores, and then come its partitions in order, marked **Active** for the one being filled or probed and **First** and **Last** for the two ends of the list. Under each partition, **Hash Bucket Pages**, named after `PvAllocateHashBucketPage` which allocates them all, lists the partition's pages of hash items. The partition's directory is one of its fields. An **Item Page** is a page the directory leads to, holding the slots for a range of buckets, and an **Overflow Page** holds the items a bucket links on to once its first is full, with how many items it holds. **Workfile Pages** lists the workfile pages the partition's rows are stored on, with how many rows each holds. **Bitmap Pages** is the block of pointers to the pages of the partition's bitmap, the bit filter a lookup checks before it reads a bucket, with a **Bitmap Page** under it for each of them. Drag the splitter between the tree and the bytes to resize the tree.

Selecting a part shows its bytes as they are at the playhead, with only that part's fields marked, each in its own colour. Clicking a marked byte selects its row: the field on a partition group or partition, the item on an item or overflow page, or the slot on a workfile page. A selected field fades the rest of the bytes so it stands out, and clicking it again clears the fade. A selected item is outlined in red instead, and only its fields keep their colours. An 8-byte value in the bytes that points somewhere is underlined, as on a memory tab, and **Ctrl+Click** follows it. A pointer into the hash table selects that part in the tree, and any other opens a memory tab or the page. **Build Side**, **Probe Side**, **Hash Bucket Pages** and **Workfile Pages** only group the parts under them, so clicking one expands or collapses it rather than selecting it. Along the top, links lead back through the parts above it to the partition group. **Back** and **Forward** at the start of that row, or the mouse's back and forward buttons, step through the parts you have visited, returning to the item or workfile slot you had selected on each.

- **Hash Table** - the operator's fields that hold the table: its partition groups, the partition mask and shift that pick a partition from a hash value, its workfile managers and the partition group in use. A **Worktable Group** shows only its bytes.
- **Accessors** - a row for each column of the rows the group stores: its name, its type, where it sits in the row, and links to the column's two value objects and to the bindings SQL Server built to read it. The type comes from those bindings, so columns the query computes, such as an aggregate's result, decode as well as the ones read from a table. The rows on the workfile pages are decoded with the same columns.
- **Partition Group** and **Partition** - the fields with their offsets and values, in the same layout as a batch's fields. A pointer is a link: one to another part of the table selects it in the tree, and any other, such as the directory, opens a memory tab. Selecting a field fades the rest of the bytes so it stands out. The partition group's fields include the expressions it runs: the **Insert Expression** copies each new row into the workfile, and in a hash aggregate the **Update Expression** updates the row of a group already held and the **Compare Expression** compares the keys. Its **Columns** read the columns of the row in the **Active Partition**, the one being filled or probed, and its **Scan Columns** those of a row read back from a partition that spilled, the **Scan Partition**. Its **Workfile Group** creates each partition's workfile.
- **Item Page** - a row for each bucket whose slot is in use, with its **Head**, the address of the bucket's first item, and for the item kept in the slot its **Next** and **Count**, how many entries it holds. Usually the slot holds the bucket's own first item, so **Head** is the slot itself.
- **Overflow Page** - a row for each item on the page, with the bucket it belongs to, its **Next** and its **Count**.

Each row shows only what is in that item, not the rest of the bucket. Expanding it lists the item's rows, each with its entry from 1 to 6, its key, the address of the row and the row's values. A badge after the address says what it points into: **Workfile** for a workfile page, **Buffer Pool** for a page in the buffer pool, or the name of the object it lands in. **Next** is a link to the item it points to, and so is **Head** when the bucket's first item is kept somewhere else. A bucket with seven rows shows six on its item page, and its **Next** leads to the overflow page holding the seventh. The colour key in the **Head**, **Next**, **Count**, **Key** and **Row** headings matches the marks in the bytes. Selecting a row outlines its item in red and marks only that item's fields. The bucket of the last insert or lookup at the playhead is marked **Insert**, **Match** or **No Match**. Clicking a row's address selects its workfile page and the slot the row is in. An address anywhere else opens a memory tab or the page.
- **Workfile Page** - the page's slots, as on a memory tab's **Workfile Page** tab. Selecting a slot marks the row's columns in the bytes and lists what each one holds.
- **Bitmap Pages** - a row for each pointer in the block, marked in the bytes, and each a link to its **Bitmap Page**. A **Bitmap Page** shows only its bytes.
- **Memory** - everything the Hash Match allocated during the run. A row for the total is followed by a row for each kind of memory. Most kinds are the parts of the hash table, found by following its pointers the same way as the tree: **Workfile Pages**, **Item Pages**, **Pointer Pages**, **Overflow Pages**, **Directories**, **Bitmaps**, **Partitions**, **Partition Groups** and **Workfile Rowsets**. Then come the **Worktable Groups**, the **Hash Iterator** itself, **Other Bucket Pages** for item, pointer and overflow pages a spill used and released between rounds, and **Other** for the rest, such as the column bindings and expressions it set up. Each row has how many allocations there were, the bytes they came to, how much was in use at the playhead and the most in use at once. Beside the table a chart plots memory in use across the query, the total and each kind, with a legend above it and the playhead marked. Hovering over a line names it and reads its memory in use at that point, and clicking the chart moves the playhead there.

Each bucket on an item page points to its first item, a block of the same size that holds up to six rows as a key and a pointer to the row. Usually the bucket's own slot is its first item. A bucket with more rows links further items one after another, kept in other pages, or in a slot no bucket was using yet. When that slot's own bucket fills later, its first item is kept elsewhere and the slot points to it. On an item page the marks show each slot's pointer to its first item, and for every item on the page its count, its link to the next item, and each row's key and pointer.

### Sort Table

A row mode Sort's sort table opens as a tab of its own. In any Full Trace, **Sort Table** on a Sort's right-click menu in the Execution Plan opens it below the plan, and **Open Sort Table** on the Sort's right-click menu among the Trace Timeline's operators opens it on the Trace Timeline. A memory tab on any part of the sort table names it in a **Sort Table** header above its bytes, with a link that opens it at that part, and **Open Sort Table** on the memory tab's right-click menu does the same. The tab follows the playhead, and **Back** and **Forward** step through the parts you have selected, as on a hash table.

The tree starts at **Sort Table**, the Sort operator itself, with **Memory** first under it and then its **Rowset** and the rowset's **Sort Descriptor**. **Runs**, **Record Pages** and **Compare Pages** only group what they hold, and open or close on a click. Selecting a part shows its bytes at the playhead with its fields marked, and clicking a marked byte selects its row, as on a hash table.

- **Sort Table**, **Rowset** and **Sort Descriptor** - the fields with their offsets and values. A pointer to another part of the sort table selects it in the tree, and any other opens a memory tab. The sort descriptor holds the number of rows the sort was set up for, the length of the fixed part of each record, and the **Cursor**, the entry the sort returns next. It also holds where each run starts: the slots **Run 0** to **Run 31**, and the **Current List** with its tail and count. Only the slots holding a run are listed. Each is marked in the bytes and is a link to its run in the tree.
- **Record Page** - the rows the sort was given, each copied into the page as a record in the order it arrived. It shows the page's slots, as on a memory tab's **Sort Page** tab. The sort keys come first in each record, followed by the sort's other columns, and each column is decoded with the type the sort itself uses for it, so a key the query calculates, such as `RIGHT(TextField, 2)`, decodes as well as a column read from a table.
- **Compare Page** - a row for each entry on the page, in the order the entries were made. An entry points to one record and to where the sort key starts inside it, holds the length of each, and links to the **Next** entry. Each row also shows the **Run** the entry belongs to and its **Position** in that run. Expanding a row lists its record's values, and the record's address selects its slot on the record page. The colour key in the field headings matches the marks in the bytes. Selecting a row outlines its entry in red and marks only that entry's fields.
- **Run 0** to **Run 31**, **Cursor** and **Current List** - the entries of one run, named after the sort descriptor field that points to its first entry, in the order their **Next** links them, which is the order the sort has put them in so far. A run has no bytes of its own, so the bytes are those of the compare page holding the selected entry, the run's first entry to start with, with the run's entries on that page marked. Selecting an entry outlines it as on a compare page, and selecting one on another page moves the bytes to that page.
- **Memory** - everything the Sort allocated during the run, laid out as on a hash table: the total, then **Record Pages**, **Compare Pages**, the **Rowset**, the **Sort Descriptor**, the **Sort Iterator** and **Other**, with the allocations, bytes, memory in use at the playhead and peak for each, and the chart of memory in use across the query beside it. Runs take no memory of their own, because their entries are on the compare pages.

The records never move. Once a page of records is full, its rows get entries and the sort links them into runs, lists in sorted order that the sort descriptor keeps in its slots like a binary counter. **Run 0** holds about one entry, **Run 1** about two, **Run 2** about four, and so on. New entries are linked into the **Current List** first. When it joins the slots it merges with the run in **Run 0**, and a run that finds its next slot taken merges with that run too and moves up, leaving the slots below it empty. Stepping through the input shows the runs build up and merge. At the end of input the runs that are left are merged into one, which the **Cursor** points to, and the sort then returns its rows by following that run's **Next** links, one row each time the **Cursor** moves on. From then on the **Cursor** run holds only the rows still to come. The entry the cursor is on, its compare page and its run carry a **Cursor** badge.

### Trace Summary

**Trace Summary**, on the Trace menu, opens a tab on the left of the query that sums up the run in panes. Each pane has a header with its name. Clicking a header opens that pane and closes the one that was open, so one pane fills the tab at a time, and clicking the open pane's header closes it. **Operators** is open to start with.

#### Operators

**Operators** lists the plan's operators in the same hierarchy as the plan, each named after its operator and node. Beside it is the class and address of the operator's iterator, the object that does its work while the query runs, such as `CQScanTopNew`, and clicking it opens the iterator. An operator is made of more than one object, and the others are listed under it:

- **Compiled Plan Object** is the operator as the plan compiled it, such as `CXteTop`. It is the part a cached plan keeps, and it holds the operator's list of output columns, listed under it as **Output Columns**.
- **Profiling Iterator** is the `CQScanProfileNew` the run wraps around the iterator to count the operator's rows for the actual plan. The operator above calls the wrapper, and the wrapper calls the iterator.

**Output Columns** lists the columns the plan compiled the operator to output, each with its name from the plan and its type. Beside each column is the class and address of its column reference, such as `CValRefOrdinal` for a column read from a table or `CValRefJoin` for a column a join outputs. An operator that passes a column on from below, as a Top does, holds the same reference as the operator below it, so the same address appears under both. Clicking a column opens its column reference as a memory tab.

After the reference comes the column's value at the playhead, or **NULL**. It is read from the operator's row buffer for a scan or seek, or from the row a hash join returns. A column a hash join reads straight from its probe input's rows is read from the record on the page, which the app reads from the database as it does to open a page, so it shows only for a page in the query's database. The value changes as the playhead moves, so stepping through an operator's calls shows each row's value in turn.

The reference is fixed when the plan compiles, so expanding a column follows it into execution:

- **Value**, for a hash join, is the column's entry in the join's output values, the object execution reads the column through.
- **Buffer Entry**, for a scan or seek, is the column's entry in the operator's row buffer, which every fetched row overwrites, with where the column sits in the stored row.
- **Reader**, for a hash join, is the object the value reads through: a `CValHash` for a column of the hash table's rows, with the row slot it reads and where the column sits in the row, or which of its variable-length columns it is, or a `CValSSTable` for a column of the probe input's rows, with its row slot. A column of the probe input's rows lists two, the `CValHashCachedSwitch` the value holds and the `CValSSTable` it picks.
- **Row Slot** is that slot in the statement's row context. Beside it is where it points at the playhead, the object and offset it points into and the address. The hash join points it at the row it returns, on every row, so it moves row by row as the playhead does. For a column of the probe input's rows it holds the input's rowset instead, which stays the same.
- **Record**, for a column of the probe input's rows, is where the rowset keeps its current record, with where the column sits in the record. Beside it is the page and slot of the record at the playhead, which moves on as the input reads each row.
- **Input Column** is the reference of the column the join took it from, the same one listed under the input operator. For a column the plan calculates, it is each column the calculation reads.

Each Full Trace compiles the query inside the recording, so the objects a cached plan keeps and reuses are recorded too.

#### Memory

**Memory** lists the objects created during the recording, or the trim, as a tree of the calls that created them. Each object is listed under the objects whose methods were running when it was allocated, outermost first. The table scan in a simple `SELECT TOP` sits under `CSQLSource`, `CMsqlExecContext`, `CExecStmtLoopVars`, `CXStmtQuery`, `CQuery`, `CQueryScan`, the Top operator's `CXteTop` and iterator, and `CXteTableScan`, and a hash join's **Hash Table › Partition Group** sits under the `CQScanHash` iterator that built it. An object created in the recording is one entry for every later call that reaches it the same way, so what it creates is listed under it. An object reached through different calls is listed again under each. A call made without an object, such as a static method, is listed by its class. An object that was not created in the recording, or the trim, is listed with its address, and clicking it opens the memory it sits in.

At each level the objects are grouped by type. A type with one object is listed as the object itself, and a type with more shows how many there are, with the objects under it. A type the app knows is named for what it is, such as **Hash Table › Partition Group** for a `CHashWorkfilePartitionGroup`, and an operator's objects are named for what they are and their operator, such as **Iterator › Top (Node 0)**, **Profiling Iterator › Top (Node 0)** and **Plan Object › Top (Node 0)**. Every object that is part of a row mode hash join's hash table is named for its part, such as **Hash Table › Item Page** or **Hash Table › Workfile Rowset**, so the pages of one kind group together. Objects on the stack are left out, with the objects they point to lifted into their place, until **Stack Objects** is turned on.

The box at the top of the pane filters the tree to the objects whose name, type or address contains what is typed, along with the objects above them. Clicking an object opens it as a memory tab.

The right-click menu of an object in either pane has **Open Memory**, **Object Graph**, which opens a graph starting from that object, and for an object that is part of a row mode hash join's hash table, **Open Hash Table**.

## Playhead

Click the ruler or a thread's header to put a playhead on the chart, and drag along either to move it. Its badge gives the position, as `sequence:steps` on the Position axis. The step back and step forward buttons move it to the start of the previous or next call on any visible thread, and double-clicking the ruler hides it again and clears the selected call and operator.

### Trimming the query

Two small handles sit either side of the playhead's triangle, at the bottom of the strip under the ruler. Drag one away from the playhead to trim the query to the stretch between them, and drag either again to move that end. Outside the trim is shaded and the playhead stays inside it, but the chart keeps its zoom. Memory History, the Memory History lane, the latch row and search then count only what happened inside the trim. Memory History and its lane keep every block the query created that changed inside the trim, even one created before it, and a reference graph is drawn from the pointers held inside it and counts only the changes made inside it, so **Reference Changes** and **Data Changes** show what was busy in that stretch. The Operators lane is not trimmed, and pointers still resolve against the whole recording. Double-click the playhead's triangle to remove the trim.

**Play** moves the playhead steadily along the chart, scrolling the view on when it reaches the edge, and stops at the end of the recording. With the query trimmed it plays the trimmed stretch over and over until you pause it. It starts from the playhead, or from the left of the view when there is none or the playhead is already at the end. Click it again to pause. Stepping pauses it too, so the playhead stays where the step put it. The step menu beside the frame buttons sets what they step to. **Tracks** steps through every tick on the operator tracks that are turned on, the same steps [Guide Mode](/docs/user-guide/query/ExecutionPlan#guide-mode) takes, and a single track steps from one of its ticks to the next. With **Tracks** or a track selected, **Play** steps through them instead, holding on each long enough for the [Execution Plan](/docs/user-guide/query/ExecutionPlan) to show the change and let it fade. A faster playback speed holds for less time.

With the memory view set to **None** and **Call Stack** off, the calls under the playhead pop out of the chart, each raised by the memory it allocated, so scrubbing along shows which part of the stack is allocating. Drag a raised call to change the angle and depth, as with the memory view. With a memory view on, the band marks the memory allocated and in use at the playhead.

::: details How this works
Each bar is one call recorded during the Full Trace replay, with where it started and ended in the recording, the instructions it executed, its thread and its place in the call tree. Positions are shared by every thread, which is why that axis lines them up, while each thread counts its own instructions.

See [How Full Trace works](/docs/deep-dives/full-trace) for the details.

## Call Stack

**View > Call Stack**, or **Call Stack** at the bottom of the right-click menu, opens a tab beneath the chart listing the calls that led to the selected call. With nothing selected the tab reads **No Call Selected**. Its tab strip has the **Decode** toggle and step back and step forward buttons, which select the previous or next call at the same depth as **Left** and **Right** do. The stack sits under a row for the selected call's thread, each call shown as the function's signature with each parameter's type and the value it was passed, coloured as in the Call Tree's signatures. A dot before each call shows its category's colour, and hovering over it names the category. A value that decodes to an object shows the object's class instead of its declared type. `this` is shown without its address, unless it decodes to something such as an operator or an index, and its address is in the call's details. The innermost call comes first, highlighted and marked with a red arrow, and each call below it is the one that called it, as a debugger lists a stack. The pane selects the same call as the chart, and opens its details beside the stack. The values decode as they do in [Arguments](/docs/user-guide/query/CallStack#arguments), and the **Decode** setting is shared. Drag the tab to dock it above, below or beside the chart, and drag the splitter between them to resize it. Its **X**, or turning **Call Stack** off, closes it.

A value in the stack that points into memory the trace recorded has a **Show Memory** button, which opens that block's bytes as a tab of its own, named after the object. Right-clicking such a value, in a call's signature or in its details, offers **Memory History**, which opens the same tab at the address it points to, including a value already shown as the object it points into. A value that points into a buffer pool page reads **Buffer Pool Frame:** with the page the frame held at that moment and how far into the page it points, such as **Buffer Pool Frame: (1:100) +0x1A0**, and the same goes for pointers in a memory tab's **Writes** and in a batch's fields. A pointer to the BUF, the buffer pool's descriptor for the page, reads **Buffer Pool: (1:100) BUF** and opens the page without selecting a record. Clicking it opens the page with the record holding that byte selected. The page opens as it is now, not as it was during the query. A page from another database, such as tempdb, is named with its database and does not open. Its tab strip has step back and step forward buttons, which select the previous or next write in the **Writes** list, so the playhead and the outline follow it. With a filter set they step through the writes the list shows. Clicking a block in the chart's memory lane opens the same tab. When the value points inside the block, or the click was part way along it, the bytes scroll to that address and it is outlined. Each block gets one tab, and its bytes follow the playhead, with the bytes each call changed marked in the call's category colour. An 8-byte value in the bytes that points into recorded memory or into a buffer pool page is underlined and drawn in grey, since it is an address rather than a value to decode. Hovering over it names what it points to, and **Ctrl+Click**, or **Open Memory** or **Open Page** on the right-click menu, follows it. Memory tabs dock and resize like the Call Stack, so they can share its tab strip or sit on another side of the chart.

While a memory tab is the one showing, the strip beneath the ruler is marked where that block was written, each mark in the colour of the writer's category, so you can see when it changes. Hovering over a mark reads the tab's name followed by **Updates**, and clicking there moves the playhead to it. With a search open as well, the search marks take the top half of the strip and the memory marks the bottom half. Widen a memory tab and its tabs appear beside the bytes. A block's own tabs, such as **BUF**, **Bindings** and **Iterator**, come first, and opening a block that has one shows it unless **Writes**, **Reads**, **Watches** or **References** is selected. **Details** gives the block's address, marked **Heap** or **Stack**, its type and length, its lifetime as the positions it was created and destroyed at, the function that created it, how many updates it had, and the functions that wrote to it with how many writes each made, coloured by category and listed in the order they first wrote. For an object on the stack the lifetime runs from the first call that held it to the end of the last, followed by how many instances it had, and the function that created it is the one whose stack holds it. It has no **Reads** or **Read By**, because reads are only recorded for heap memory. It also gives how many times the block was read, and under **Read By** the functions that read it with how many reads each made, in the lighter shade of their category colour. **Writes** lists every write to the block with its position, function, address, length and value. The value is the bytes written as hex, or decoded as the type of a watch pinned on those bytes. Clicking a write moves the playhead to it, scrolls the bytes into view and outlines them, and the pin at the end of a write adds a watch on those bytes. The **Function** and **Address** boxes filter the list, **Show Writes** on a function's right-click menu in **Details** or clicking a byte in the hex fills them in, and right-clicking a write offers **Filter To Function** and **Filter To Address**. The position, address and value columns sort when their headers are clicked. **Reads** lists each call that read the block, with the position of its first read, the function, the call, the address and length of the bytes it read, and how many reads it made. A call that reads several fields is one row covering all of them. Its function is shown in a lighter shade of its category colour, and the list filters, sorts and outlines the bytes read the same way. **Show Reads** on a function's right-click menu under **Read By** fills in its **Function** box. **Watches** lists the pinned watches with an editable label, the type the value is decoded as and its value at the playhead, and a button to clear each one. **References** lists the 8-byte values in the block that point into recorded memory or into a buffer pool page, each with its offset, the address it holds and what it points to, so two pointers to objects of the same type can be told apart. The box above the list filters it to the pointers whose target or address contains what is typed. Expanding a pointer lists the pointers found from the address it points to, read at the playhead, so a chain of structures can be followed as far as it goes. A pointer into the middle of a block, including one into the tab's own block, lists the pointers from that address to the end of the block, with offsets counted from that address. Collapsing a pointer and expanding it again reads it afresh. A pointer to an address already followed on the path, or to the start of the tab's own block, is marked **(Cycle)** and can still be expanded. A pointer whose target has changed since the pointer was written is left out, here and in the underlines in the bytes. An example is a pointer a compiled plan keeps into compile memory that was freed and has since been reused for a page. **Graph** beside that box, **Open Reference Graph** on a memory tab's right-click menu, or right-clicking a block in the Memory History lane opens the block's pointers as a graph in a query tab of its own, docked along the bottom of the query so the Trace Timeline stays in view while the graph follows the playhead. It can be dragged elsewhere like any other tab, and a second graph opens beside the first. Along its top the graph's name is followed by how many objects it shows, with a spinner while it is being worked out, and a search box on the right lists the boxes whose names or addresses match. Choosing one scrolls the graph to its box and outlines it. **Object Graph**, on the Trace menu, opens a graph that starts from a call rather than a block: the first call on the Trace Timeline, which with **Crop To Query** on is the start of the query itself. Its first box names that call's function, and its connectors lead to the objects the call was given, each labelled **this** or with the register or stack location the argument was passed in, such as **RDX**. From there it reads like any other graph. The graph is drawn from every pointer the block's fields held across the recording, or across the trim, so its shape stays put while the playhead moves and only the values in its boxes change. Each field that held a pointer is a box naming the type it points to, with the address it holds at the playhead beneath, and each buffer pool page is a shaded box naming the page. A box shows the object as a whole, and where in it a pointer lands is written on the pointer's connector. A scan's array of column bindings is the exception: expanding it shows each binding as a box of its own, **ColumnBinding[0]**, **ColumnBinding[1]** and so on, each with the pointers it holds. A box whose object has watches pinned on it lists them under its address, each with its label, or its offset and type when it has none, and its value at the playhead decoded the same way as on the memory tab's **Watches**. A column binding's box lists only the watches that fall inside that binding. A field that is empty at the playhead keeps its box, with its name greyed out and no value, because it is not set yet, has been cleared, or what it pointed to has been freed. A box that only ever holds one object shows that object for its whole life, from allocation to free, even before anything on the path points at it, so you can open it whenever it exists. A page used by a sort or a workfile is named **Sort Page** or **Workfile Page**. A field that pointed to objects of different types names them all, separated by a slash, until the playhead reaches one of them. A BUF whose frame was set before the recording, because its page was already in the buffer pool, still points to its frame, taken from where the query found the page. A field that moves from object to object, such as the BUF of the page being scanned, is one box whose value changes as the playhead moves, and the fields under it follow whichever object it points to at the playhead, so the frame under a BUF changes with it. The tab's own block starts expanded, and the arrow at the right of any other box expands it to show its fields, or collapses it again. A box whose objects never held a pointer has no arrow. Right-clicking a box offers **Expand All**, which expands it and everything under it, and **Collapse All**, which collapses it and everything under it and closes the objects on its left. Right-clicking the first box does this for the whole graph. Neither is available while **Reference Changes** or **Data Changes** is on, as those already expand as far as they need to. **Select** on a box's right-click menu starts the graph again from that box's object, the one it holds at the playhead, and the graph's title follows it. **Reset**, on the right-click menu of the graph's background, goes back to the object or call the graph was opened on. A very large graph stops growing once it reaches its limit, which the count along its top notes, and it fills each column before starting the next, so what it leaves out is furthest from the start. Each pointer is a stepped connector with the field it is held in written above it, and the offset it lands at when that isn't the start. A field that moves around inside the same object, such as a pointer stepping through the rows of a page, shows the offset it points to at the playhead, so the label changes as the playhead moves. A connector whose pointer went on to point somewhere else is drawn in orange, with how many times it did beneath it. Only moves you would see in the box count, so a move made while the path led to a different object is left out. Only a move from one place to a different one counts. Clearing the field, setting it back to the same place, and pointing it back into its own object, as an empty list does, are not changes. The call that first sets a field is setting it up, so none of its writes to that field count, however many it makes. After that every move counts, including several within one call. Nothing from the start of the query's shutdown onwards is counted. When an object holds several pointers into one other object, each field gets its own connector, labelled with the field and where in the other object it points, and they fan out and collect back into that object's single box like the rungs of a ladder, starting below the box so the first does not look like a direct connection. Several dashed links, or links on the left, from one object to another share a connector instead, labelled with the first and how many there are, and hovering over the connector lists them all. A pointer to objects already on the graph, by another path or round a cycle, is a dashed connector to the box that shows them rather than a second box, so the graph stops there. That holds wherever in the object the pointer lands, and a box shows the object's own address. Dashed connectors are drawn lighter than solid ones, and run on their own verticals between a box and its solid connectors, so they never lie on top of a solid one. One going down leaves below the middle of its box and arrives above the middle of its target. One going up leaves above and arrives below, and turns closer to the box. One that would have to cross a column of boxes to reach its target runs along the gap between two rows instead, so it never passes behind a box. A dashed connector's label is only written, beside the box it leaves, while the pointer is over the connector. Labels on solid connectors that would land on top of each other are stacked. Hovering over any connector, or its label, draws it in green on top of the others, and its tooltip names the boxes at either end, the field and how many changes it had. **Reference Changes** and **Data Changes** on the graph's tab strip narrow the graph to what changed, expanding as far as they need to, with the objects on the shortest way to each. Only one can be on at a time, and with neither on the graph shows everything you have expanded. **Reference Changes** shows the pointers that changed. **Data Changes** shows the objects whose other fields changed after the call that set them up and before shutdown, leaving out the last call when it clears a field for good, and hovering over a box's name gives how many data changes it had. A field whose objects are all already on the graph is left out, along with the path to it, so if an object and one of its fields both point to the same BUF only the object's own pointer is drawn. The dashed connectors are left out too. The arrow at the left of any box shows the objects that point to it in the column to its left, and the same arrow on each of those shows the objects that point to them, further left. For a box out on the right of the graph they start on the row below it, and their connectors arrive below the middle of the box, so they stay clear of the connector from the box's own parent. The arrow is only there when something not already on the graph points to the box. Each connector on that side carries its label beside the object it comes from, since several objects can point into the same box. An object already on the graph is not added again, so the graph never loops back on itself. Objects allocated in the same place that point to it at different times share a box, which shows whichever one points to it at the playhead. The mouse wheel scrolls the graph, **Shift** + the mouse wheel scrolls it sideways, and dragging its background moves it. **Ctrl** + the mouse wheel zooms in and out at the pointer, and **Shift** + drag draws a rectangle and zooms to it. Right-clicking the graph, or a box, offers **Zoom to 100%** and **Zoom to Fit**. Zoomed out too far to read the detail, each box shows only its name, written larger, and the connector labels and the band along the top are hidden. While the labels are readable, a thin band along the top of each box is a small timeline of the recording, or of the trim. A thin line under the band is the lifetime of the object the box shows, from when it was allocated to when it was freed, over a light track that runs the width of the band. The line is in the colour of the category of the function that allocated the object, or darker grey for a page or an object whose function has no category. It is marked wherever the box moves to point somewhere else, and wherever the object's other fields change, each mark in the colour of the category of the function that wrote it, with nothing marked from the start of shutdown. It is shaded grey up to the playhead, so you can see how far the playhead is from the next change. Clicking a box's name opens what it points to at the playhead as a memory tab, or opens the page. Hovering over a box outlines the object it shows at the playhead in the Memory History lane, the same outline as hovering over the lane itself, and scrolls the lane to it when it is out of view. When the playhead is outside the box's lifetime it outlines the object the box last held, or the first it will hold if the playhead is before them all. Clicking a target opens it as a memory tab or opens the page, and selecting a pointer at the top level outlines its bytes. Every BUF the query fetched is recorded too, named after the page it held, such as **BUF (1:43)**, and its memory tab has a **BUF** tab as well. It names the page the BUF holds at the playhead, which opens it, and reads its frame address and its latch: held shared and by how many, held exclusively or released, whether threads are waiting, the latch's owner and waiter list, and the raw state. The bindings a scan uses to copy each row into its row buffer have a **Bindings** tab. On the bindings object it gives the number of columns and a link to the column bindings. On the column bindings, and on the row buffer itself, it lists each bound column with its ordinal, type and size, where it sits in the record (or **Variable** and its number among the variable columns), where its status, length and value go in the row buffer, its flags with **Length** shown when the length is written separately and **By Reference** when the value is a pointer rather than a copy, and a link to its **Column Attributes**. A colour key in a heading shows the colour that field is marked in. Selecting a column marks its bytes in those colours: every field of its column binding, or its status, length and value in the row buffer. Links along the top open the bindings object, its column bindings and the row buffer. It also gives the BUF's database ID, partition, status, error code, state history, read time in microseconds, when it was last used and recovery unit. While the tab is selected those fields are marked in the bytes. A field that **DBCC PAGE** prints in its BUF section carries that name too, such as **Status (bstat)**. An iterator has an **Iterator** tab holding a row of tabs. The first is named for the operator, such as **Top (Node 0)**, and is a table of the fields known for its class, each with its offset and value and marked in the bytes in the colour beside it while the tab is selected. Selecting a field outlines its bytes. Every iterator, a profiling iterator included, has **Inputs**, the array of the iterators it reads its rows from, and the query's execution context, which every iterator in the run shares. A scan or seek has no inputs, and a profiling iterator's one input is the iterator it wraps. An operator's inputs are the profiling iterators of the operators below it, which in turn wrap their iterators. A scan or seek adds its rowset, prefetch manager, row buffer, row bindings and the row it sends to the client. A Top adds its TOP count expression, and a hash join its input and output values and the fields that hold its hash table. A field that points to an operator's plan object or one of its iterators is named for it, such as **Plan Object › Top (Node 0)**, so a profiling iterator shows the iterator it wraps as **Iterator › Top (Node 0)** and the profiling iterator above it. A field that points to recorded memory is a link that opens it. The tabs after the first show what those fields point to, read at the playhead, rather than marking bytes. **Inputs** lists the iterators in the inputs array, each with its address. A scan or seek has **Row Bindings**, the columns its bindings copy into its row buffer, set out as on the **Bindings** tab. A hash join has a tab for each of its input and output values arrays, listing each entry with the output column it holds where that is known. A profiling iterator has only its fields and **Inputs**. **Plan Object** at the end of the row of tabs opens the operator's compiled plan object, named **Plan Object › Top (Node 0)** and so on, as a memory tab of its own. Its **Plan Object** tab holds a tab of its fields, marked in the bytes, and **Output Columns**, the columns it was compiled to output, each with its type, its reference and the operator that produces it. **Lineage** has a tab for each column that draws the pointers execution follows to reach the column's value, starting at the operator's iterator. From there it runs through the iterator's **Inputs** and the profiling iterators to the iterator below that produces the column, and into the arrays of values, the readers, the slot of the statement's row context they read, and the row buffer entry that holds the column. A join also shows its own input value, which points into the row buffer of the operator below it. Only the pointers themselves are drawn, not the plan object, execution context and table the app follows to find them. Each box is an object, named for its operator or for what it is to the column, with the fields that lead on as rows of name, pointer and value. A line runs from each field to the object it points to, or to the field inside it, and is dashed where it is a slot number rather than a pointer, or goes back to an object already drawn. A column a scan or seek reads straight from the page, rather than from its row buffer, runs from the iterator to its rowset, the rowset's current row and the record that row is on. A column the plan calculates runs to each column its calculation reads, followed the same way. A field inside an object is drawn as a row of that object's box. The chain is read again as the playhead moves, so when a pointer moves to another object the drawing follows it. A column that a batch mode operator hands to a row mode one goes through the batch to row adapter between them. Its chain runs from the adapter to its output value and its row buffer, which holds the row the adapter returned last, and on to the batch it is reading, its cursor and the column map that names the vector each column comes from, then to the batch's selection and that vector, at the row the cursor is on. Stepping through the rows moves the cursor along the batch. Between two batch mode operators the chain stops at the iterator, because each works on a whole batch of rows at a time. A value read from the row buffer of the operator below is shown there as well, and a value on a record is read from the page, for a page in the query's database. The pointers and values are read at the playhead, so stepping through the rows shows the value change. Clicking a box's name or a pointer opens it as a memory tab. Each field on the chain is checked against the functions known to write it. A field last written by a different function is listed under **Fields Written By Unexpected Functions** above the drawing, and its name in its box is red, with the function that wrote it when the pointer is over the name. It is a sign that the recording comes from a SQL Server build that lays the object out differently, so the chain may not be reading what it says. Its fields are its node id, the plan objects of its inputs, the query it belongs to and its list of output columns, and for a Top its TOP count expression and for a scan or seek the rowset it opens. A plan object is only recorded when the plan was compiled inside the recording. Positions are shown as sequence and step in hex, and every position is a link that moves the playhead there. Clicking a function in **Details** moves the playhead to its first write, or under **Read By** its first read. Right-clicking a position or a function in **Details** gives **Zoom to**, which zooms to the call and selects it, and **Call Stack**, which moves the playhead there and opens the Call Stack. A function also gives **Find**, which finds the call in the Call Tree. For a function that wrote or read more than once these act on its first write or read and read **Zoom to First** and **Call Stack First**. Right-clicking the address gives **Find**, which finds the calls that used it. Hovering over a position marks it on the chart and shows the chart's map of the whole recording with the position on it, and hovering over a function in **Details** highlights its writes, or under **Read By** its reads, in the lanes.

Selecting a call further up the stack, with **Up** or by clicking it in the pane, keeps the stack as it is and moves the selection along it, so **Down** comes back the same way. Selecting a call that is not on the stack, by clicking its bar or with **Left** and **Right**, starts a new stack ending at that call. The pane follows the [category filter](/docs/user-guide/query/CallStack#filtering-by-category) and **Scope**, so its calls are the ones drawn in the chart above it.

Clicking a call selects it in the chart, the Call Tree and **Arguments**, the same as clicking its bar, and opens its details beside the stack. These show its category, its module, `this` and the value it returns. They also show its **Call Id**, the trace positions it started and ended at, how many instructions it executed, and its **Arguments**, each with its number, the register or stack location it was passed in, its type and its value. The value it returns is shown the same way, starting with the register it came back in. When the value returned or an argument points into recorded memory or a buffer pool page, what it points to is a link on the line beneath it. Right-clicking a call gives **Open In Call Tree**, **Zoom**, which fits the chart to that call, **Scope**, which scopes the chart to its function the same as the chart's own [Scope](#scoping-to-a-function), **Copy Signature**, which copies the line as it reads, with its types and values, **Copy Symbol**, which copies the function's name, and **Copy Address**, which copies the function's address. The copy button at the end of each call copies its signature, and every value in the details has a copy button beside it too. The value a call returned is in its details rather than the stack. The details are headed by the function's name. Right-clicking a value in the stack gives **Copy Decoded**, **Copy Value** and **Find**. In the details, the positions the call started and ended at are links that move the playhead there, and right-clicking one gives **Zoom to** and **Call Stack**. Right-clicking `this`, the value returned or an argument gives **Find** when it is an address. The selected call's function is highlighted in the stack in the same way as a search match, until the details are closed.
